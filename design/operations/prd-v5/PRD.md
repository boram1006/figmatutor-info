## 1. 릴리즈 개요

### 1.1 목적
본선 진출 팀이 1차 지원서의 기존 작성 내용을 승계해 최종보고서를 완성하고, 최종 심사에 필요한 산출물을 하나의 패키지로 제출할 수 있도록 한다.

### 1.2 기본 구성
1. 1차 지원서의 **7개 content section을 그대로 승계**한다.
2. 최종보고서에 본선용 신규 section 1개를 추가해 **총 8개 content section**을 구성한다.
3. 본선 최초 진입 시 기존 7개 section이 완료 상태이므로 content completion은 **7/8**에서 시작한다.
4. 8개 content section 이후 **9번째 UI 단계**에서 최종 보고서·발표자료·데모 URL·소스코드 링크를 하나의 패키지로 최종 제출한다.

### 1.3 진입 경로
**마이페이지 → 내 지원 현황 → 지원서 카드 → 이어 작성하기**

## 3. A-30. 내 지원 현황

### 3.1 화면 목적
본선 진출 지원서의 최종보고서 진행 상태와 제출 상태를 보여주고, 작성·조회·재제출 workflow로 진입시킨다.

### 3.2 진입 및 기본 구조

#### 3.2.1 마이페이지 네비게이션
마이페이지 좌측 네비는 다음 구조를 유지한다.
- 내 정보
- **내 지원 현황**
- 내 팀
- 팀빌딩 지원 현황

#### 3.2.2 최종보고서 카드
본선 진출 지원서가 있으면 최종보고서 카드가 노출된다.

#### 3.2.3 하위 화면 컨텍스트
A-31/A-32 내부에서는 기존 화면과 동일하게 **지원하기 컨텍스트를 유지**한다.

### 3.3 상태 정의

| 상태 | 표시 | CTA |
|---|---|---|
| 본선 진행중·작성중 | Red `본선 진행중` + content completion | `이어 작성하기 →` |
| 제출완료 | Green `제출완료` | `제출 내용 보기 →` |
| 제출완료 후 변경 미반영 | Warning `재제출 필요`만 표시 | `수정사항 제출하기 →` |
| 본선 미진출 | Gray `본선 미진출` | `제출 지원서 보기 →` |

### 3.4 상태 규칙

#### 3.4.1 진행률
- 최초 content completion = **7/8**
- 신규 5번 section 완료 후 = **8/8**

#### 3.4.2 제출 후 수정
- 제출 후 수정 시 내부 workflow state는 기존 제출본을 유지한 채 `SUBMITTED + CHANGED_AFTER_SUBMIT`으로 관리한다.
- 단, A-30 화면에서는 Green `제출완료`를 함께 노출하지 않고 **Warning `재제출 필요`만 표시**한다.
- 수정분은 자동 반영하지 않으며 **재제출해야 심사에 반영**된다.
- `재제출 필요`는 필수 확인 액션이므로 **Warning semantic**을 사용한다.

### 3.5 상단 안내
> 10월 16일까지 제출을 완료해주세요. 제출완료 이후에도 제출 마감 전까지는 수정 가능합니다.

### 3.6 공통 예외
- 로딩/에러는 기존 공통 양식을 사용한다.
- v5 화면별 별도 로딩/에러 정책은 정의하지 않는다.
- Empty state는 실제 필요가 확인될 때 추가한다.

## 4. A-31. 최종보고서 스텝 폼

### 4.1 화면 목적
1차 지원서의 기존 7개 section을 승계해 수정할 수 있게 하고, 신규 section 1개를 추가 작성한 뒤 최종 제출 패키지 단계로 이동하게 한다.

### 4.2 스텝 구성
1. 기본 정보
2. 서비스 정의
3. 문제정의
4. AI서비스 구성계획
5. 신규 메뉴
6. 활용 Data 및 연동시스템
7. 확대전개 가능성
8. 기대효과
9. 최종 심사 제출 패키지

### 4.3 데이터 승계 규칙

#### 4.3.1 기존 section
- 1차 지원서 **7개 항목을 그대로 승계**한다.
- 승계된 7개 항목은 read-only가 아니라 **수정 가능**하다.

#### 4.3.2 신규 section
- 최종보고서에는 **5번 신규 메뉴 1개만 새로 추가**된다.
- 신규 메뉴의 추가 정보는 서버가 내려준다.
- UI에서 별도의 완료 판정 규칙을 구현하지 않는다.

#### 4.3.3 최초 완료 상태
- 본선 최초 진입 시 content completion은 **7/8**이다.

### 4.4 스텝 상태 표현

#### 4.4.1 완료 상태
- 완료: 보라 ✔
- 미완료/현재: 회색 번호

#### 4.4.2 9번 패키지
- 회색 번호
- `4종 통합` 배지
- 하위 4종 산출물의 상태 표시

### 4.5 완료 판정
**section 완료 여부는 서버가 판정한다.**

UI는 서버가 전달한 완료/미완료 상태만 표시하고, required/optional 판정식을 자체 구현하지 않는다.

### 4.6 디자인 범위
- SECTION 2~8 내부 폼 필드 상세 구성은 v5 디자인 범위에서 제외한다.
- v5에서는 step navigation의 section 이름/상태와 workflow 연결을 다룬다.

## 5. A-32. 최종 심사 제출 패키지

### 5.1 화면 목적
최종 심사에 필요한 4종 산출물을 준비·확인하고, 저장·최종 제출·수정 후 재제출을 수행한다.

### 5.2 패키지 구성

| # | 구성요소 | 확정 동작 |
|---|---|---|
| 1 | 기획/개발 최종 보고서 | `최종 보고서 확인` → SECTION 1~8 통합 **기존 read-only modal 재사용**. `발표 자료 초안 생성 (.pptx)` → AI가 수정용 PPTX 생성 |
| 2 | 발표 자료 | **등록은 PDF only**. AI 생성 PPTX는 수정용이며 사용자가 PDF로 변환해 등록 |
| 3 | 서비스 데모 URL | URL + `테스트 ↗` |
| 4 | 소스코드 저장소 | **링크 입력칸만 제공**. provider 제한/검증 없음 |

- 완료 = Green ✔
- 미등록 = Gray

### 5.3 최종 보고서 확인

#### 5.3.1 Modal 재사용
- 신규 전용 modal frame을 생성하지 않는다.
- **기존 read-only modal을 재사용**한다.

#### 5.3.2 표시 방식
- 현재 A-32 위에 modal/overlay로 연다.
- SECTION 1~8 내용을 통합해 읽기 전용으로 보여준다.
- edit control은 제공하지 않는다.
- 닫으면 A-32 context를 유지한다.

### 5.4 발표자료 정책

#### 5.4.1 AI 생성물
- AI 생성물은 `.pptx`
- 목적은 **수정 가능한 발표자료 초안 생성**

#### 5.4.2 최종 등록물
- 최종 등록은 **PDF only**
- 업로드 안내: `최대 50MB · PDF 파일만 업로드 가능`

### 5.5 저장 및 제출

#### 5.5.1 버튼 상태

| 시점 | 저장 | 제출 |
|---|---|---|
| 4종 미충족 | `저장` 사용 가능 | `최종 패키지 일괄 제출하기 →` 비활성 |
| 4종 충족 | `저장` 사용 가능 | `최종 패키지 일괄 제출하기 →` 활성 |
| 제출완료·변경없음 | `저장` 사용 가능 | `제출 완료됨 ✓` muted 비활성 |
| 제출 후 수정 | `저장` 사용 가능 | `변경사항 다시 제출하기 →` Red primary 재활성 |
| 제출 마감 후 | **버튼 없음** | **버튼 없음** |

#### 5.5.2 저장 규칙
- 화면 용어는 `임시 저장`이 아니라 **`저장`**으로 통일한다.
- `저장`은 Final Submit과 별개다.
- 제출 마감 전까지 저장할 수 있다.
- 저장만으로 submitted state가 되지 않는다.

#### 5.5.3 제출완료 안내
`A-32_submission-package_SUBMITTED` 하단 안내 문구는 다음으로 한다.

> 마감 전까지 모든 항목을 수정할 수 있습니다. 수정 후에는 다시 제출해야 합니다.

### 5.6 제출 후 수정 및 재제출

#### 5.6.1 변경 감지
제출 완료 후 항목을 수정하면 기존 제출본을 유지한 채 `SUBMITTED + CHANGED_AFTER_SUBMIT` 상태로 표현한다.

#### 5.6.2 재제출
- 변경사항은 자동으로 심사에 반영되지 않는다.
- 사용자가 `변경사항 다시 제출하기 →`를 실행해야 최신 내용이 심사 제출본이 된다.

### 5.7 제출 마감 후

#### 5.7.1 기본 정책
기존 서비스에서 정의하는 마감 시각을 따른다.  
v5 UI에 별도 canonical timestamp를 새로 노출하지 않는다.

#### 5.7.2 상태 정의
- DEADLINE_PASSED를 제출/미제출 상태로 분리하지 않는다.
- **단일 `A-32_submission-package_DEADLINE_PASSED` 상태**를 사용한다.

#### 5.7.3 조회 범위
- 마감 시점의 최종 제출본을 조회한다.
- 전체 read-only다.
- edit control은 제공하지 않는다.

#### 5.7.4 액션
다음 버튼은 모두 제거한다.
- `저장`
- submit
- re-submit
- disabled `제출 마감됨`

#### 5.7.5 안내 문구
> 제출이 마감되었습니다.

## 6. 공통 상태 및 생성 규칙

### 6.1 상태 semantic
- 완료/제출완료 = Green
- 진행중 = Red
- 미제출/미등록 = Gray
- 재제출 필요 = Warning
- A-30의 제출 후 변경 미반영 상태에서는 `제출완료` Green 표시를 병기하지 않고 `재제출 필요` Warning만 노출한다.

### 6.2 제출 이벤트
- Save와 Final Submit은 서로 다른 이벤트다.
- Final Submit만 workflow의 제출 상태를 변경한다.
- 제출 후 수정은 기존 제출본을 삭제하지 않고 `SUBMITTED + CHANGED_AFTER_SUBMIT`으로 표현한다.

### 6.3 버튼 최소 폭
- 버튼 최소 가로 폭은 **84px**이다.
- 라벨이 짧아 content 기반 너비가 84px 미만이어도 84px 이상을 유지한다.
- 라벨/패딩으로 필요한 너비가 84px을 넘으면 내용에 맞게 확장한다.
- 디자인 생성 시 짧은 라벨을 이유로 84px 미만의 버튼을 만들지 않는다.

### 6.4 Figma 생성 원칙
Figma 생성은 다음 순서를 따른다.

`INSTANCE_REUSE → CLONE_COMPOSE → NEW_CONSTRUCTION`

snapshot에서 확인하지 않은 nodeId/nodeName은 추측하지 않는다.
