# Figma 컴포넌트 라이브러리 제작 가이드

사용자가 지정한 [컴포넌트 정리 레퍼런스](https://www.figma.com/design/8MaPdwz8IbmpbzUyWNEd8c/?node-id=27-786)를 참고하여 컴포넌트를 카테고리별로 정리한다.
이 링크는 제작 레퍼런스이며 작업 대상이 아니다. 실제 대상은 `harness.config.json`의 `figma.fileKey`로 확인한다.

## 원본에서 확인한 구성

전담 에이전트가 지정 노드의 구조와 실제 캡처를 확인했다. 지정 노드는 `02 Components` 페이지의 `Pagination` 문서이며 전체 카테고리 분류표가 아니다.

- 제목·용도·가이드 액션 (`27:788`) → `Dot` 하위 유형 (`27:797`) → 크기 라벨과 실제 사례 인스턴스 (`27:803`) → 실제 variant set (`27:814`) → `Resource` (`27:847`) 순서다.
- Pagination Dot은 Size Normal/Small × Color Adaptive/White의 4종 variant를 제공한다. Resource에는 크기/색 조합별 Active/Inactive 세트 4개가 있다. 이 개수와 속성을 다른 컴포넌트에 강제하지 않는다.
- 실제 캡처에서는 흰 외곽 문서, 큰 제목과 짧은 설명, 연회색 본문 패널, 흰 사례 카드, 중앙에 놓인 견본과 넓은 수직 여백이 계층을 구분한다. 밝고 어두운 견본을 식별할 수 있는 배경을 사용한다.
- 주변 노드의 이름/타입만 추가 조회했다. 주변 컴포넌트 내부·캡처, 가이드 액션의 목적지, 토큰 바인딩은 조사하지 않았다. 아래 역할별 분류는 원본의 전체 분류를 복제한 것이 아니라 하네스의 적용 규칙이다.

이번 조사 근거는 `design/operations/inspect-component-guide/result.json`에 기록했다. 운영 기록을 초기화해도 이 가이드의 관찰 범위는 유지하며, 새 작업에서 원본의 변경 여부와 필요한 세부 사항을 확인한다.

## 적용 범위

- 사용자 방향 선택 이후 `components` 단계에서 적용한다. 대표 시안 비교 전에 전체 라이브러리를 만들지 않는다.
- 제품 컴포넌트의 색·타이포·형태는 선택된 시안과 실제 토큰을 따른다. 레퍼런스에서는 카테고리 구분과 문서 구성 방식을 참고한다.
- 요구사항의 `componentIds`에 필요한 컴포넌트만 만든다. 문서를 채우려고 불필요한 카테고리나 variant를 추가하지 않는다.
- 토큰 문서는 [토큰 라이브러리 가이드](token-library-guide.md)를 함께 적용한다.

## 제작 절차

1. 지정 노드의 구조와 실제 캡처를 읽기 전용으로 확인한다(op:extract/screenshot 스펙). 확인한 정보와 하네스의 적용 제안을 구분해 작업 결과에 남긴다. 원본에 접근하지 못하면 그 사실을 기록하고 원본 배치를 확인했다고 보고하지 않는다.
2. 요구사항의 컴포넌트를 역할별로 분류하고 작업 계약에 카테고리 → componentId 목록을 작성한다. 예를 들어 액션, 입력·선택, 내비게이션, 콘텐츠 표시, 피드백, 오버레이로 구분할 수 있다. 이는 하네스의 분류 예시이며 원본에서 확인한 카테고리 목록은 아니다. 실제 제품에 맞게 합치거나 나눈다.
3. `02 Components` 페이지에 카테고리별 Section을 만들고 각 컴포넌트 문서를 구분해 배치한다. 각 문서는 이름·역할·사용 기준 → 필요한 하위 유형 → 속성 라벨과 실제 사용 예시 → 마스터와 variant/state → 필요한 Resource 순서로 구성한다. 관련 가이드 링크는 실제 목적지가 있을 때만 제공하고, Resource는 실제 재사용 하위 자산이 있을 때만 만든다. 기존 노드가 있으면 ID를 유지하며 정리한다.
4. 상태·크기 등 실제 지원하는 속성은 라벨을 붙인 행·열로 비교할 수 있게 전시한다. 반복 문서 영역은 Auto Layout을 사용하고 긴 설명·컴포넌트가 잘리지 않도록 내용에 맞게 높이를 조정한다.
5. 마스터는 실제 COMPONENT/COMPONENT_SET으로 만들고 문서의 사용 예시는 해당 INSTANCE로 연결한다. 그림이나 분리된 복제 프레임을 재사용 컴포넌트의 증거로 쓰지 않는다. 제품 컴포넌트의 semantic 변수·텍스트 스타일 바인딩을 유지한다.
6. `catalog.json`에는 기존 계약대로 실제 nodeId, states, height, semanticTokens를 기록한다. 카테고리 배치와 문서 nodeId는 작업 결과에 기록한다. 카테고리 정리를 위해 승인 입력이나 완료 판정을 임의로 바꾸지 않는다.

## 검증

- 요구사항의 componentId가 카테고리 목록과 실제 마스터에 빠짐없이 연결되고 중복 마스터가 없는지 확인한다.
- catalog의 states와 실제 variant/state가 일치하고, 사용 예시가 해당 마스터를 참조하는지 확인한다.
- 카테고리별 실제 캡처를 열어 제목 위계, 상태 라벨, 정렬, 간격, 겹침·잘림을 확인한다. 문제는 캔버스에서 수정한 뒤 재캡처한다.
- `design/operations/<task-id>/result.json`에 카테고리 매핑, 문서/마스터 nodeId, 캡처 경로, 실제 관찰과 미해결 사항을 남긴다.
- 기존 스냅샷 추출과 `npm run check:components`도 실행한다. 카테고리 배치와 문서 가독성은 현재 자동 게이트가 검사하지 않으므로 게이트 PASS만으로 이 가이드 준수를 보고하지 않는다.
