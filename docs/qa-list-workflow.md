# QA 리스트 생성 워크플로우

새 릴리즈가 나올 때마다 QA agent가 source-backed QA 체크리스트를 생성하고, 사람이 직접 실행·기록하는 흐름.

---

## 역할 분담

| 단계 | 담당 | 설명 |
|---|---|---|
| QA 리스트 생성 | QA agent | PRD + SCREEN + 확정 프로젝트 규칙을 source로 TC 초안 생성. 이전 릴리즈는 granularity/regression 참고만 사용 |
| 리스트 검토·보완 | 사람 | 누락 케이스 추가, 우선순위 조정, Skip 사유 결정 |
| 실제 QA 실행 | 사람 | 브라우저에서 직접 확인하며 Pass/Fail/Skip 기록 |
| Fail 이슈 정리 | 사람 + QA agent | Fail 항목 설명 보완, 재현 조건 정리 요청 가능 |

---

## 입력

QA 리스트를 생성하려면 다음 입력을 사용한다.

### 필수
- **릴리즈 PRD** — 대상 화면, 상태 머신, UI 매트릭스, 기능 범위
  - 예: `design/operations/prd-v5/PRD.md`
  - 또는 대화에 직접 붙여넣은 PRD 블록

### 선택 (있으면 TC 품질 상승)
- **이전 릴리즈 QA 파일** — 동일 화면의 기존 TC 패턴 재사용
  - 예: `design/operations/qa/ver.1.md` (저장해 둔 경우)
- **변경점 메모** — "이번에 추가된 기능", "기획 변경된 부분"
- **테스트 서버 URL** — 결과 기록 파일에 자동 삽입

---

`design/operations/qa/<릴리즈식별자>.md` 파일 1개.

## 절차

### 1단계 — 화면 목록 확정

PRD에서 대상 화면 ID를 추출한다.

```
SITEMAP §5-1 Archetype 매핑을 참조해
각 화면의 주요 기능 영역(화면 진입 / 목록 / 입력 / 저장 / 제출 / 에러)을 분류한다.
```

### 2단계 — 기능 영역별 TC 생성

아래 표는 **TC 자동 생성 목록이 아니라 coverage 확인용 질문 목록**이다. 각 항목은 PRD/화면/확정 문서에 동일한 요구가 있을 때만 TC로 만든다.

- source가 없으면 TC를 만들지 않는다.
- 이전 릴리즈에 있었다는 이유만으로 현재 릴리즈 TC에 복사하지 않는다.
- 일반 QA 관례는 누락 가능성을 발견하는 질문으로만 사용한다.
- source가 없지만 확인할 가치가 있어 보이면 `OPEN_QUESTION`으로 남기고 expected result를 발명하지 않는다.

#### 공통 영역 (해당 요구가 source에 있는 화면만)
| 영역 | 확인 항목 |
|---|---|
| 화면 진입 | source에 정의된 정상 진입·로딩·실패·빈 상태가 있는가? |
| 네비게이션 | source에 정의된 GNB/현재 페이지/이동 동작이 있는가? |
| 에러 처리 | source에 500/503·타임아웃·재시도 등 구체 오류 동작이 정의되어 있는가? |
| 텍스트 | PRD/화면에 명시된 문구·정보가 정확히 노출되는가? |

#### 목록/테이블 화면 (해당 구조와 요구가 source에 있을 때)
| 영역 | 확인 항목 |
|---|---|
| 데이터 표시 | 컬럼 항목 정확성, 미입력 `-` 표시, 긴 텍스트 레이아웃 |
| 상태 표시 | 미심사 / 심사중 / 심사완료 / 총점 표시 |
| 정렬 | 기본 정렬 기준, 동점 처리, 저장 후 재정렬 |
| 선택 | 강조 표시, 선택 전환 |

#### 입력 화면 (해당 입력 규칙이 source에 있을 때)
| 영역 | 확인 항목 |
|---|---|
| 입력 방식 | 증감 버튼, 키보드 직접 입력 |
| 입력 범위 | source에 정의된 최솟값/최댓값/허용 형식만 검증 |
| 상태 변경 | source에 정의된 입력 후 UI 상태 변화만 검증 |
| 저장 | source에 정의된 저장 동작·성공/실패 결과만 검증 |
| 저장 안 됨 보호 | source에 이탈 경고/저장 보호가 명시된 경우에만 검증 |

#### 제출 화면 (해당 제출 규칙이 source에 있을 때)
| 영역 | 확인 항목 |
|---|---|
| 제출 버튼 | 조건 미충족 시 비활성, 조건 충족 시 활성 |
| 제출 동작 | source에 정의된 확인/취소/중복 방지 동작만 검증 |
| 제출 성공 | source에 정의된 성공 후 상태·잠금·조회 전환만 검증 |
| 제출 실패 | source에 실패 UI가 정의된 경우에만 검증 |

#### 심사/채점 화면 (해당 심사/채점 규칙이 source에 있을 때)
| 영역 | 확인 항목 |
|---|---|
| 진행률 | 초기 계산, 완료 수 / 전체 수 정확성 |
| 항목 평균 | 내 평균 점수 = 저장된 전체 지원서 기준 평균 |
| 다음 지원서 | 버튼 노출 조건, 이동 동작, 마지막 케이스 숨김 |
| 동시 접속 | 동시성/다중 탭 정책이 source에 명시된 경우에만 검증 |

### 3단계 — 우선순위 배정

| Priority | 기준 |
|---|---|
| P1 | 핵심 기능 동작, 데이터 정확성, 사용자 차단 가능 오류 |
| P2 | 상태 표시, UI 일관성, 보조 기능 |
| P3 | 레이아웃 엣지케이스, UX 세부사항 |

### 4단계 — Skip 후보 표시

**이미 source-backed TC로 생성된 항목 중** 실행 환경 때문에 재현이 어려운 경우에만 `**재현 필요` 또는 `**별도 확인 필요` 주석을 붙이고 Result를 `QA : Skip`으로 초기화한다.

예:
- PRD에 명시된 서버 오류/타임아웃/저장 실패 케이스이나 테스트 환경에서 재현 불가
- PRD에 명시된 동시 접속·경쟁 상황이나 재현 환경 없음
- 기획 변경으로 source 자체가 폐기된 기존 TC

Skip 후보 목록을 이유로 새로운 TC를 생성하지 않는다.

### 5단계 — 파일 저장

```
design/operations/qa/<릴리즈식별자>.md
```

릴리즈 식별자 규칙: `v<버전>-<yyyymmdd>` 예: `v6-20261015`

## 이전 릴리즈 패턴 요약 (ver.1~3 분석)

아래는 과거 릴리즈에서 관찰된 **coverage 참고 패턴**이다. 현재 릴리즈 PRD에 같은 요구가 확인되는 항목만 재사용한다. 패턴 자체는 현재 릴리즈의 product requirement 근거가 아니다.

### 1차 심사 / 최종 심사 공통 패턴 (ver.1, ver.3)
화면 진입(목록 조회 정상/실패/빈상태, 기본 선택, 진행률) → 목록(표시정보, 상태3종, 선택, 이동, 정렬) → PDF/Loop 뷰어(조회, 페이지이동) → 심사표(호출, 조회, 표시, 진행률) → 점수 입력(방식, 범위, 상태변경) → 총점/평균 → 저장(버튼, 성공, 실패, 보호) → 다음 지원서 → 전체점수 현황보기 → 최종 제출

### 전체점수 현황 패턴 (ver.1, ver.3)
화면 진입 → 테이블(표시정보, 총점 색상) → 점수 입력(테이블 내 직접) → 총점 계산 → 저장 → 정렬 → 지원서 보기 링크 → 미입력 경고 배너 → 최종 제출(버튼 상태, 팝업, 성공/실패) → 페이지 이탈 보호 → 동시성

### 팀빌딩 패턴 (ver.2)
접근 제어(오픈 전/정시) → 상태 관리(마감 처리) → 데이터(정렬, 로딩, 수치) → 액션(지원서 보기, 지원하기, 취소, 대기신청) → 동시성 → 보안(로그인 체크) → UI(카운트다운, 카드, 로딩)

### 발표/결과 화면 패턴 (ver.2)
데이터(합격팀 정보, 탈락팀, 정렬) → 시간(카운트다운 기준/종료/버튼 변경) → 액션(버튼 동작, 중복 클릭) → UI/UX(로딩, 텍스트 오탈자) → API 에러 → 네비게이션 → 부하 테스트

### 실제 Fail에서 얻은 regression-risk 패턴

ver.1~3의 과거 QA는 현재 requirement source가 아니지만, **어디에서 결함이 잘 발생했는지**를 보여주는 regression evidence로 사용할 수 있다.

반복해서 우선 확인할 위험:
- **boundary input**: min/max에서 값이 실제로 바뀌지 않았는데 저장 상태가 변경되는 문제
- **invalid numeric state**: 0점처럼 허용되지 않아야 할 값의 입력/저장
- **cross-screen synchronization**: 한 화면에서 수정한 값/상태가 다른 화면에 즉시 반영되지 않는 문제
- **save/submit distinction**: 저장과 확정 제출의 상태가 섞이는 문제
- **transition edge**: 마지막 항목, 마감 직전/직후, 제출 후 수정처럼 state boundary에서 발생하는 문제

현재 릴리즈 source가 해당 상태를 실제로 정의할 때만 TC로 생성하되,
같은 수준의 boundary/cross-screen case가 빠지지 않았는지 self-check한다.

## 사용 예시

```
"v6 PRD 기반으로 QA 리스트 만들어줘"
→ PRD 파일 경로 또는 내용을 제공
→ QA agent가 위 절차대로 source trace가 있는 케이스와 실행용 체크리스트 생성
```

```
"최종 심사 페이지 QA 리스트 업데이트해줘, 이번에 자동저장 기능 추가됐어"
→ 변경점을 알려주면 해당 TC 수정 + 신규 TC 추가
→ 기존 Pass/Skip 결과는 유지, 변경된 부분만 갱신
```
